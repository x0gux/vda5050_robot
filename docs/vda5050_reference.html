1. 토픽 규칙 TOPIC CONVENTION

VDA5050의 모든 통신은 아래 템플릿의 MQTT 토픽으로 이뤄집니다. 한 칸이라도 틀리면 로봇/관제가 못 알아듣습니다.

uagv/v2/{manufacturer}/{serialNumber}/{messageType}

구간값 (본 패키지)규칙
uagv고정VDA5050 표준 토픽 접두어. 일부 구현은 vda5050을 쓰기도 함 — 같은 규격, 다른 접두어이며 관제와 로봇이 합의하면 됨
v2고정프로토콜 메이저 버전 (v1/v2/v3 — 토픽에 박혀 있어 하위호환 관리에 쓰임)
{manufacturer}study제조사 식별자. 소문자 권장 (관제가 소문자로 정규화하는 관례가 많음)
{serialNumber}SIM-001로봇 개체 번호. 제조사+시리얼이 로봇의 고유 키
{messageType}아래 표state / connection / visualization / order / instantActions

메시지 타입 5종 — 방향과 주기

messageType방향주기/시점QoS역할
state로봇 → 관제상시 (본 패키지: 500ms)0위치·배터리·진행률·에러 전체 상태
visualization로봇 → 관제state보다 빠르게 (선택)0지도 렌더링용 위치 스트림
connection로봇 → 관제접속/복구 시 (retain)0ONLINE / OFFLINE / CONNECTIONBROKEN
order관제 → 로봇작업 지시 시1노드/엣지 경로 + 노드별 액션
instantActions관제 → 로봇즉시 필요할 때1비상정지(faxEStop), 오더 취소 등

💡 connection만 retain을 쓰는 이유: 늦게 구독한 관제도 "이 로봇 ONLINE"을 즉시 알게 하려고. state는 매초 새것이 오므로 retain 불필요.

2. 메시지 카탈로그 MESSAGES

로봇 → 관제…/state 초 2회 · 가장 중요한 메시지 ▾
필드타입설명
headerIdint토픽별 단조 증가. 유실/중복/순서 판별의 기준
timestampstringISO-8601 UTC (…Z)
versionstring"2.0.0"
manufacturer / serialNumberstring토픽과 동일한 로봇 식별자
opStatestringIDLE / WORKING / ERROR — 표준 필드가 아니라 관제가 추론한 값 (FATAL·ERROR 에러→ERROR, 진행중→WORKING). 본 패키지는 편의상 함께 실어 보냄
orderId / orderUpdateIdstring / int현재 수행 중인 오더와 그 갱신 버전
lastNodeId / lastNodeSequenceIdstring / int마지막으로 도달한 노드 (이동 중엔 직전 노드 유지)
agvPositionobject{x, y, theta, mapId, positionInitialized} — theta는 +x축 기준 도(°)
batteryStateobject{batteryCharge: 0~100, charging: bool}
actionStates[]array{actionId, actionType, actionStatus} — WAITING/RUNNING/FINISHED/FAILED…
nodeStates[] / edgeStates[]array경로 진행률 — PENDING / RUNNING / FINISHED. 비어 있으면 로봇이 하는 일 없음(IDLE 판정 근거)
errors[]array{errorLevel, errorType, errorReference, errorDescription}

    

  


  

    

      로봇 → 관제…/connection
      이벤트성 · retain ▾
    

    

      
connectionState 하나가 전부: ONLINE(정상) / OFFLINE(브로커에는 살아있지만 로봇 프로세스가 죽었을 때 브로커가 띄우는 유서) / CONNECTIONBROKEN(통신 두절 보고).

      

    

  


  

    

      관제 → 로봇…/order
      경로 오더 · QoS 1 ▾
    

    

      

        
필드설명

        
orderId오더 고유번호. 새 주행엔 항상 새 orderId (완주한 오더 재발행은 중복 무시됨)

        
orderUpdateId같은 orderId로 경로를 바꿀 때 1씩 증가. 로봇은 더 큰 값만 수용

        
nodes[]{nodeId, sequenceId, released, nodePosition:{x,y,theta,mapId}, actions[]}

        
edges[]{edgeId?, sequenceId, startNodeId, endNodeId, released} — 노드들을 잇는 이동 구간

        
sequenceId실행 순서 — 오더 전체에서 단조 증가 (관례: 노드 1,3,5… / 엣지 2,4…)

        
actions[]노드 도달 시 실행: {actionId, actionType, blockingType} — pick/drop/charge…

      

      
⚠️ 로봇은 sequenceId 순서대로만 진행하고, busy 상태에서 다른 orderId는 거절합니다(관제에 409).

      

    

  


  

    

      관제 → 로봇…/instantActions
      즉시 동작 · QoS 1 ▾
    

    

      

        
actionType동작파라미터

        
faxEStop비상정지 activate → FATAL 에러 + 즉시 정지 + 활성 오더 폐기. deactivate → 해제(수동 재출발 필요)[{key:"activate", value:true|false}]

        
cancelOrder현재 오더 폐기 (에러 없음, IDLE 복귀)없음

      

      

      

    

  


  

    

      로봇 → 관제…/visualization
      위치 스트림 ▾
    

    

      
state의 부분집합(agvPosition 위주) — 지도를 부드럽게 그릴 때 씁니다.

5. 에러 레벨과 safePLC SAFETY

  

    

      
errors[] 레벨 의미

      

        
errorLevel관제 화면로봇 행동

        
WARNING주황 — 참고원칙: 작업 지속 (장애물·STO는 safePLC가 보호정지/감속)

        
ERROR빨강 — 실패주행 차단, 해제 대기

        
FATAL빨강 — 즉시 대응즉시 정지 + 인터락 (E-stop)

      

      
관측된 실물 사례: 충전 도킹 중 STO 워닝(0x207)은 WARNING — 작업 지속. 같은 그림이 본 시뮬레이터에 구현돼 있습니다.

    

    

      
학습 지도 (mapId: study_map)

      

      
N4가 초록(충전 스테이션). 오더는 이 노드 좌표를 nodePosition에 담아 발행합니다.
